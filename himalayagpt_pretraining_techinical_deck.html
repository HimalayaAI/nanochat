Model intro

HimalayaGPT 0.5B is a Nepali and Devanagari-focused decoder-only language model stack trained from scratch with Andrej Karpathy's nanochat, then instruction-tuned and packaged for both Hugging Face and llama.cpp.

Architecture: GPT-style causal transformer, 15 layers, 2048-token context, 32K vocabulary.
Base pretraining checkpoint: `himalayagpt-0.5b`.
Instruction-tuned checkpoint: `himalayagpt-0.5b-it`.
Local inference path: `himalayagpt-0.5b-it-gguf` for llama.cpp.
End-to-end pipeline: corpus preparation, PyTorch training through Karpathy's nanochat, SFT, HF export parity, and GGUF serving.

Transformer Internals

nanochat is GPT-style, but not plain GPT-2

Model block details

Rotary embeddings instead of learned absolute position embeddings.
RMSNorm and QK normalization.
Untied input embedding and output `lm_head` weights.
`relu^2` MLP activation.
No bias in linear layers.
Value embedding path on alternating layers.
nanochat/gpt.py
class GPTConfig:
    sequence_len = 2048
    vocab_size = 32768
    n_layer = 15
    n_head = 8
    n_kv_head = 8
    n_embd = 1024

# attention:
# q/k/v projections → rotary → QK norm → FA3 or SDPA

# optimizer:
# matrix params → Muon
# embeddings/scalars/head → AdamW

PyTorch Module View

The architecture maps cleanly to familiar `nn.Module` blocks

Embedding`nn.Embedding` maps token IDs into the residual stream; output projection is untied.
AttentionQ/K/V `Linear` layers, rotary embedding, QK norm, then FA3 or PyTorch SDPA fallback.
MLPBias-free linear layers with `relu().square()` activation and projection back to model width.
Head`lm_head` returns logits over the 32K vocabulary and slices away any padding.

nanochat-style PyTorch modules
class GPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.transformer = nn.ModuleDict({
            "wte": nn.Embedding(cfg.vocab_size, cfg.n_embd),
            "h": nn.ModuleList(Block(cfg, i) for i in range(cfg.n_layer)),
        })
        self.lm_head = Linear(cfg.n_embd, cfg.vocab_size, bias=False)
block-level mental model
def forward(self, idx, targets=None):
    x = self.transformer.wte(idx).to(COMPUTE_DTYPE)
    for block in self.transformer.h:
        x = block(x)          # RMSNorm → attention → MLP
    logits = self.lm_head(norm(x))
    if targets is None:
        return logits
    return F.cross_entropy(
        logits.flatten(0, 1),
        targets.flatten(),
        ignore_index=-1,
    )
PyTorch audience anchor: every component is inspectable `nn.Module` code Readable enough to teach from
PyTorch Forward Pass

The core training step is still the PyTorch loop everyone recognizes

simplified training step
model = torch.compile(model, dynamic=False)

for step in range(num_iterations):
    x, y = next(train_loader)       # [B, T]
    logits = model(x)               # [B, T, vocab]
    loss = F.cross_entropy(
        logits.flatten(0, 1),
        y.flatten(),
        ignore_index=-1,
    )
    loss.backward()
    optimizer.step()
    optimizer.zero_grad(set_to_none=True)

PyTorch mechanics

`torch.compile` reduces Python overhead in the model and optimizer path.
BF16 is selected through nanochat's explicit `COMPUTE_DTYPE` instead of autocast.
Targets can be masked with `ignore_index=-1`, which is important for packed SFT batches.
The same PyTorch fundamentals apply: tensors, modules, losses, optimizers, and distributed launch.
For PyTorch community: “LLM training is still PyTorch fundamentals at scale.” Compile, dtype, packing, optimizer
PyTorch Runtime Stack

Performance comes from stacking small PyTorch decisions

Runtime choices

`torch.compile(model, dynamic=False)` because training batches keep fixed shapes.
`torchrun --standalone` for distributed launch, even when the first run is single GPU.
Flash Attention 3 on Hopper-class GPUs, PyTorch SDPA fallback elsewhere.
Explicit BF16 compute path: master weights remain optimizer-friendly while matmuls run in compute dtype.
Muon for matrix parameters, AdamW for embeddings, scalars, and unembedding.
Best-fit packed data loading and prefetching to minimize wasted context tokens and GPU idle time.
launch pattern
uv run torchrun --standalone --nproc_per_node=1 \
  -m scripts.base_train -- \
  --depth=15 \
  --max-seq-len=2048 \
  --device-batch-size=32 \
  --total-batch-size=65536 \
  --window-pattern=L \
  --device-type=cuda

Scaling Rules

nanochat derives training horizon from model scale

scripts/base_train.py
target_tokens =
    target_param_data_ratio * scaling_params

total_batch_size =
    round_power_of_2(B_ref * (target_tokens / D_ref) ** 0.383)

num_iterations =
    target_tokens // total_batch_size

Explain simply on stage

Depth is the main model-size dial.
Width and attention heads are derived from depth and head dimension.
Token horizon follows a target tokens-to-parameters ratio.
Batch size and learning rates are scaled from a reference model.
Good audience phrase: “We did not hand-tune every knob; nanochat gives a scaling policy.” Scaling laws in practice

How to read this slide

`train/tok_per_sec`: throughput stayed near the high-20K token/sec range, with occasional checkpoint/eval/data stalls.
`train/loss`: the curve trends down overall, while local spikes reflect shuffled packed examples rather than a single smooth curriculum.
`train/dt`: per-step latency was mostly stable after warmup, with spikes from validation, I/O, or logging interruptions.
`train/mfu`: shown as zero because the NVIDIA GB10 peak-FLOPS table was undefined in the run environment, not because the GPU was idle.
W&B logs are evidence for training health, not just vanity charts Throughput + loss + dt tell the run story

Serving lessons

Use `llama-completion` for one-shot prompts.
Use `--jinja --single-turn` to respect the chat template.
On Apple Metal, tune GPU offload with `-ngl`; lower if output becomes blank or control-character-like.
Quantized serving requires its own smoke test, not only HF tests.
GGUF repo: himalaya-ai/himalayagpt-0.5b-it-gguf Q8_0 model was verified locally through llama.cpp
GGUF Runtime Caveat

GGUF is portable, but nanochat currently needs our llama.cpp fork

What users must know

These GGUF files do not run on upstream `ggml-org/llama.cpp` yet because nanochat is not supported there.
Use the fork: `github.com/HimalayaAI/llama.cpp`.
LM Studio, Ollama, Open WebUI, and other tools that bundle vanilla llama.cpp will not work until upstream nanochat support lands.
The GGUF embeds the nanochat chat template and EOT token, so `--jinja --single-turn` matters for prompt rendering.

Quantization notes

BF16Recommended reference GGUF, numerically closest to HF Transformers.
Q8_0Practical default: about 533MB and near-identical quality for demos.
Q4_K_MSmallest file, but math quality degrades more noticeably.
F16Avoid: squared-ReLU MLP can overflow F16 and produce NaN logits.
Key message: this is a custom architecture release, not a generic llama.cpp drop-in yet Runtime docs prevent support pain
Debugging Story

The failure modes were useful signals

1. Base repetitionRepeated characters were a clue about model stage and training maturity.
2. SFT works nativeRaw nanochat checkpoint produced coherent chat outputs.
3. HF mismatchBad outputs pointed to export/tokenizer/generation path issues.
4. Parity testsLogits equality gave confidence in the fixed HF export.
5. GGUF servingllama.cpp required command and backend-specific validation.
When a model “looks broken,” separate model quality from tokenizer, template, dtype, export, and serving-runtime bugs.

Limitations

What this model is, and what it is not

Strengths

End-to-end Nepali-focused training stack works.
Instruction-tuned model can answer simple Nepali and English prompts.
HF and local GGUF artifacts are available for community testing.
Training and export tooling is now reusable.

Known limits

0.5B is small; reasoning and factuality are limited.
Nepali evaluation sets are noisy and still incomplete.
SFT improves interaction but does not replace stronger pretraining scale.
Serving backends can require exact command guidance.
Be honest here; it makes the roadmap more credible Proof of capability, not final frontier
